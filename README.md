# Wayfinder routing integration

The UCL Wayfinder HTML uses the graph extracted by `gemini-map/pdf_to_json_map.py` as the routing source of truth. The frontend translates its room and connector selections to graph node IDs, requests a route from FastAPI, and transforms the returned graph coordinates into the HTML map's SVG coordinate system.

## Run the integrated prototype

Install the backend requirements in the Python environment used to run the server:

```bash
python -m pip install -r backend/requirements.txt
```

Start the API from the backend directory:

```bash
cd backend
python -m uvicorn main:app --reload
```

In another terminal, serve the frontend directory:

```bash
cd frontend
python -m http.server 5500
```

Open `http://localhost:5500/web.html`. The API defaults to `http://localhost:8000`; the frontend can override this with `?api=http://localhost:8000`. The API allows the local frontend origin on port 5500 and the common Vite/React origins on ports 5173 and 3000.

Run the backend tests and sample routes from `backend/`:

```bash
python -m unittest discover -s tests
python sample_run.py
```

## Data flow

1. `gemini-map/map_graph.json` is generated by the PDF extractor and contains the shared flat graph (`floors`, `nodes`, and `edges`). The backend defaults to this file. Override it with `MAP_GRAPH_PATH` if needed.
2. `GET /map` exposes the graph's floor and node catalog to the frontend. It derives a page number for nodes from their floor when the extractor omitted the node-level `page`.
3. `frontend/route-node-map.json` maps the HTML's room and transition IDs to exact graph node IDs. It also defines the HTML-floor-to-PDF-page mapping and per-floor display transforms.
4. Before requesting a route, the HTML checks that both mapped IDs exist in `/map`. It then posts those IDs and supported access preferences to `POST /route`.
5. The backend finds a shortest path over same-floor graph edges and configured transfer edges. Its response contains route node IDs, ordered points, floor segments, and directions.
6. The HTML maps segment pages back to floors and transforms graph percentage coordinates to the SVG coordinates used by the displayed map.

## Floor and node mapping

The Wayfinder's floor IDs are intentionally not the PDF page numbers:

| Wayfinder floor | Extracted PDF page |
| --- | ---: |
| E | 1 (Ground floor) |
| D | 2 (First floor) |
| C | 3 (Second floor) |
| B | 4 (Third floor) |
| A | 5 (Fourth floor) |

Maintain that mapping in `frontend/route-node-map.json`. Room mappings use exact curated IDs, including aliases where the labels differ (`E14` maps to `E14 (Middle)`, and `E15` maps to `E15 (Post Finance Safety)`). Stair and lift IDs are explicitly mapped in the `connectors` section. Do not infer routes from visual proximity or label similarity: update the curated mapping whenever a new HTML destination is added, and verify every ID against `/map`.

The file's `transforms` map each graph point `(x, y)` to an SVG point:

```text
svgX = xScale * x + xOffset
svgY = yScale * y + yOffset
```

These transforms are calibrated per floor and should be visually checked whenever the HTML map or extracted PDF changes.

## Floor transfers and routing filters

The extractor creates same-floor edges only. `backend/data/floor_transfers.json` supplies explicit cross-floor links between stair/lift landings; these links are added only to routing and are not guessed from coordinates. Verify each connector pair against the building plans before deployment. Override the configuration file with `FLOOR_TRANSFERS_PATH`.

Same-floor edges marked `blocked: true` are excluded. Ordinary routes allow edges with unknown accessibility, while step-free requests require each walking edge to have `wheelchair_accessible: true`. Cross-floor step-free links must be lifts explicitly marked accessible. Edges marked `requires_id_card: true` are excluded when the request indicates no card.

The current extracted map has no confirmed wheelchair-accessibility values on its 275 walking edges. Therefore, step-free requests may return `no_route` until those edge attributes are verified and populated. Transfer accessibility also needs building-level confirmation. A self-selected card category is only reduced to a card/no-card boolean; it does not authenticate the user or prove real door access.

Live closures, incidents, timed access, “avoid reported problems,” amenities, and arbitrary map points are not connected to backend routing yet. Routes can start or end only at mapped rooms and stairs/lifts. The interface calls out these current limits rather than suggesting that local demo markers affect the backend route.

## API contract

`GET /health` returns a basic server status. `GET /map` returns `metadata`, `floors`, and nodes containing the fields needed by the frontend (`id`, `name`, `kind`, `x`, `y`, `floor`, and `page` where available).

`POST /route` accepts:

```json
{
  "start": "p001_ground_floor_room_e20",
  "destination": "p002_first_floor_room_d14",
  "wheelchair_required": false,
  "has_id_card": false
}
```

A successful response has `status: "ok"`, ordered `node_ids`, `edge_ids`, `points`, `segments`, `steps`, and `floor_changes`. Unreachable filtered paths return `status: "no_route"`; unknown node IDs return HTTP 404. Invalid map or transfer data is reported as an API error rather than silently producing a route.
